### Q1：Tool、MCP、Skill 有什么区别？

**简答**

Tool：进程内函数调用，直接注册 schema。MCP：工具的**发现与调用协议**，本地 stdio 或远程 HTTP 都行，harness 把它的工具转成普通 schema 喂给模型。Skill：一份渐进式加载的说明书（SKILL.md）加可选脚本。

**扩展分析**

其实把这三个放在一起看，它们的发展史就是一部 **prompt 经济学**史。早期大家各写各的 tool，格式五花八门；Anthropic 定了 MCP 标准解决互操作，2025 年各家疯狂上 MCP 服务。但很快暴露出问题：每轮调用 LLM 都要把所有 MCP 工具的 name、参数、description 塞进 prompt——而这一次调用里大部分工具根本用不上。纯 token 浪费不说，还稀释注意力、拖慢首 token。Anthropic 自己在《Code execution with MCP》那篇 blog 里承认了这一点，给出的药方是**渐进式加载 + 多用代码执行**；后来发布的 Skill 就是这个思路的落地：默认只给模型一个名字和一句话描述，模型判断相关了再去读 SKILL.md，需要细节再去翻 reference 文件。

说实话，这个思想和操作系统里的按需分页一脉相承：**上下文窗口就是内存，工具说明书就是按需换页的代码段**。全量加载等于启动时把整个磁盘读进内存——没有操作系统敢这么干，但 2025 年一半的 agent 是这么干的。我项目里的 `skill_loader.py` 就是按这个思路实现的。

所以准确的结论不是「MCP 死了」，而是：**退场的是 model-facing 的工具面**——把几十个工具定义直接怼进 system prompt 这种玩法；**protocol-facing 的连通层还在**，甚至反过来成了 skill 的分发通道。能量化地感受下差距：GitHub 官方 MCP server 早期光工具定义就要吃掉五万量级的 context token，后来瘦身到两万三；而一个写着「用 gh CLI」的 SKILL.md 大约两百 token——而且工具定义是**每个 session 开工前就要付的租金**，不管这次任务碰不碰 GitHub。

Skill 为什么便宜，机制上要讲对：skill 大量是**纯说明书，不注册任何函数**；就算附带脚本，那些脚本也是**被 bash 调用的字符串**，不进 tool schema。它归约到 `Read` + `Bash`——恰好是后训练分布里密度最高的两样东西，所以新增一个 skill 的接口成本接近零。但别说「完全没有分布税」——准确的说法是：**税没有消失，是从结构化通道搬到了自然语言通道**。「知道该读哪份 SKILL.md」这个决策不在 schema 里，在描述里，所以它不吃 tool-selection 的税，改吃 retrieval / instruction-following 的税——而那恰好是模型最擅长的通道。这个版本还能**预测失败**：skill 一多，触发准确率会因为描述之间的语义竞争而掉，不是 schema 膨胀——这是可测的。

工程上我对 MCP 的批评也从「协议不好」收窄成了「用法不好」——协议本身有 Inspector 可以调试，远程 MCP 也可以 curl。它真正的问题是两个约定：`mcp__{server}__{tool}` 的命名空间前缀，人为把每个工具推离后训练分布；工具描述是**供应商写的**，质量不受你控制，却承担了全部语义负担；再一次挂几十个，选择错误率和 context 成本同时爆炸。反过来说，**把 MCP 工具控制在五个以内、描述自己重写一遍、按需加载，分布税就从灾难性降到可容忍**——补救方向是规范化使用，不是「MCP 不能用」。

**追问预测**

- *那 MCP 还有价值吗？* → 有：跨组织接第三方服务、不归你管的能力。但要用得规范——少挂、重写描述、按需加载。我自己更常用的是另一个选项：一个普通 HTTP API 加一份写给模型看的 markdown 文档，很多时候够用。
- *Skill 和 RAG 有什么区别？* → 检索对象不同：RAG 检索的是「知识」，skill 检索的是「能力说明书」。但机制上确实是同一套惰性加载思想。

### Q2：你怎么决定一个能力做成 tool、MCP 还是 skill？

**简答**

高频、核心、参数简单的 → 内置 tool；能力在外部、不归你管的（第三方服务、别的团队维护的系统）→ 走协议或普通 API；低频但流程复杂、说明书很长的专业能力 → skill。

**扩展分析**

决策变量其实就三个：**调用频率、说明书体量、所有权**。

- 高频的，说明书再短也得常驻 prompt——因为它每轮都可能被用到，惰性加载省不了钱，反而多一次「先读说明书」的往返。
- 低频的，说明书再详细也不能常驻——按需加载，不然每轮都在为十年用一次的能力付 token 税。
- 所有权是走协议的硬理由：能力不归你管、升级节奏不归你定，那就只能走某种接口约定——注意这时 MCP 也不是唯一选项，一个普通 HTTP API 加一份写给模型看的文档经常更省事。

说实话，很多团队上 MCP 是「为了架构而架构」——本地一个函数能解决的事非要起一个 server，白付序列化、进程管理、运维三份成本。我的原则是 **locality first**：能本地不起进程，能代码执行不走协议。协议是最后的手段，不是起手式。

**追问预测**

- *MCP 的实际接入体验如何？* → 协议本身不难（我仓库里有最小 server/client 示例），坑在生态质量：很多 MCP 服务的工具描述写得很随意，直接拉低模型选工具的准确率——接进来之前先改它的 description。

### Q3：function call 的原理是什么？模型是怎么学会调工具的？

**简答**

宿主程序把工具 schema（name/parameters/description）放进 prompt，模型输出结构化的 `tool_calls`，宿主解析、执行、把结果作为 `role=tool` 消息回传，模型接着生成。模型会调工具靠的是后训练阶段大量工具调用轨迹的训练。

**扩展分析**

这里有个被广泛误解的点：function call 不是 API 的魔法，**模型的输出仍然只是文本**——`tool_calls` 只是训练时约定好的特殊文本格式，由推理框架解析成结构化对象。这个认知的直接推论是：**工具调用的可靠性本质上是模型后训练的结果**。后训练里工具轨迹足够多、格式 reward 足够严的模型，调用就稳；反之怎么调 prompt 都救不回来。也不是救不了吧，但是精度就只能说……

所以工程上遇到模型乱调工具，排查顺序就是 01 Q5 那棵二分树：**先问换个更强的模型能不能好**——能，是分布问题，别在 prompt 上耗；不能，是描述/schema 有歧义，改描述。都排完还不行，才轮到框架层兜底：我的 executor 解析失败时会把错误原样回传给模型让它自己修正，实测大部分错误一轮就能自愈；正则兜底是最后手段，分布外的 case 永远修不完。

**追问预测**

- *tool 结果太长怎么办？* → 截断 + 引导模型用 grep/read 按需取细节。原则是「结论进上下文，细节留在磁盘」——和 skill 的惰性加载同一个思想。
- *并行 tool_calls 怎么处理？* → 独立调用可以并行执行，但回传消息必须保持 tool_call_id 一一对应、整组连续，不然一些模型 API 会直接报错（这个约束在我的 memory 压缩逻辑里也有体现）。
